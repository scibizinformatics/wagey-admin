# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Wagey Web Admin: a Quasar 2 / Vue 3 SPA (JavaScript, not TypeScript) that is the admin dashboard for the Wagey payroll/HR product. It talks to a separate Django REST backend (`staging.wageyapp.com` by default) for auth, employees, attendance, scheduling, leave requests, payroll/disbursement, and admin settings.

## Commands

```bash
npm install          # postinstall runs `quasar prepare`
npm run dev           # quasar dev — dev server with hot reload + API proxy
npm run start          # webpack serve directly (rarely needed; `npm run dev` is the normal entry point)
npm run lint          # eslint over src*/**/*.{js,cjs,mjs,vue}
npm run format         # prettier --write across the repo
npm run build          # quasar build -> dist/spa
npm run serve:prod     # build then serve dist/spa via server.js (PORT env, default 8000)
```

Note: README.md's "serve the production build" section says `npm run build && PORT=8000 npm start` — that's stale/wrong, `npm start` just runs webpack serve. The actual prod-serve command is `npm run serve:prod` (or `npm run build && node server.js`).

There is no real test suite (`npm test` is a no-op placeholder) — do not assume Jest/Vitest config exists. Lint is the only automated check: `eslint.config.js` is flat config (Quasar recommended + `vue/flat/essential` + prettier skip-formatting), and a single file can be checked with `npx eslint src/pages/AttendancePage.vue`. A legacy `.eslintrc.js` (downgrading `no-unused-vars`/`no-empty` to warnings) also sits at the repo root, but ESLint 9 ignores it once `eslint.config.js` exists and `npm run lint` passes `-c ./eslint.config.js` explicitly — editing `.eslintrc.js` changes nothing.

Lint is not only a separate command: `quasar.config.js` sets `eslint: { warnings: true, errors: true }`, so `@quasar/app-webpack` runs `eslint-webpack-plugin` inside `npm run dev` and `npm run build`. A lint *error* therefore fails the build and shows in the dev overlay — `npm run lint` just gets you the same result faster than a rebuild.

Docker: `docker compose -f docker-compose.prod.yml up --build -d` builds and serves on port 8000 via `server.js` (a hand-rolled static file server with SPA fallback, not `quasar serve`).
The `Dockerfile` is a two-stage build (node:20-alpine builds `dist/spa`, the runtime stage copies only `dist/spa` + `server.js` and has a `wget` healthcheck on port 8000). The root `nginx.conf` is *not* part of it — nothing in `Dockerfile`, `docker-compose.prod.yml` or `fabfile.py` references that file, so don't read it as the serving config.

Deployment to the remote host is via Fabric (`fabfile.py`, Python — needs the `venv`/`requirements.txt` at repo root), not part of the JS app; only touch it if asked about deploys.

## Architecture

**Build tooling**: this project uses `@quasar/app-webpack` (Webpack), not Vite. `.env` is *not* auto-loaded — the `VITE_WS_URL` value inside `.env` itself is ignored at runtime. Runtime config (`API_BASE_URL`, `VITE_WS_URL` fallback) is baked in at build time via `webpack.DefinePlugin` in `quasar.config.js`, keyed off `process.env.*` read at build time on the host machine — set real env vars, don't edit `.env`. `.env` is git-ignored (a developer's copy stays local); the reference copy is `.env.example`, which documents both keys and is the file to update when one changes. `VITE_WS_URL` itself is a live, wired-up feature, not dead weight: `src/composables/useWebSocket.js` (reconnect-with-backoff WS client) reads it, and `src/composables/useNotifications.js` builds on that to connect to `ws/notifications/?token=...&company=...`, consumed by `MainLayout.vue` and `DashboardPage.vue`. `devServer.proxy` has a matching `/ws/notifications` context entry (with `ws: true`) alongside the HTTP prefixes.

**Path aliases**: `@/*` maps to `src/*` (see `jsconfig.json` / webpack alias in `quasar.config.js`). Quasar's own conventions also make `boot/`, `pages/`, `layouts/`, `components/`, `stores/`, `css/`, `assets/` resolvable as bare specifiers, and the codebase also imports many things via the equivalent `src/...` path (e.g. `src/boot/axios`, `src/composables/page/useCompany`) — both styles appear interchangeably, follow whichever the surrounding file already uses.

**Routing** (`src/router/`): hash-mode history by default (`vueRouterMode: 'hash'` in `quasar.config.js`; only switches to real history mode if `VUE_ROUTER_BASE`/`VUE_ROUTER_MODE=history` env vars are set). `router/index.js` has a global `beforeEach` guard that redirects to `login` when a route declares `meta.requiresAuth` and the auth store has no token. **That guard is live**: the `/app` parent route sets `meta: { requiresAuth: true }`, and Vue Router merges `meta` down the matched chain, so the whole shell including the nested `/app/payroll` subtree is covered by that one declaration. It was inert for a long time — no route set the flag, so the condition was permanently false and what actually bounced an unauthenticated visitor was the axios 401 interceptor, after the entire admin shell had rendered. Because the guard reads `authStore.isAuthenticated`, anything that ends a session must clear the *store* (`authStore.clearToken()`), not just delete the localStorage key — `MainLayout`'s `logout()` used to do the latter and only worked because it followed up with a full page reload.

Top-level route groups:
- `/` (`AuthLayout`) → login
- `/app` (`MainLayout`) → dashboard, employees, `employees/invite` (`InvitePage.vue`, backed by `useInvites.js`), attendance, schedule, manning, requests, deductions, announcements, admin-settings, `audit` (`AuditPage.vue`, the shift-assignment trail), and a nested `/app/payroll` subtree (`DisbursementShell.vue` + child pages: list, review/:id, payslips/:id, funding/:id, disburse/:id, complete/:id)
- a catch-all `/:pathMatch(.*)*` → `ErrorNotFound.vue`

The sidebar's grouping in `MainLayout.vue` (Overview / Workforce / Payroll / Communication / Administration) is a hand-maintained array in that file, not derived from `routes.js` — adding a route does not add a nav entry.

**Page-name vs. UI-label drift**: `DeductionsPage.vue` (route `deductions`, nav label "Deductions") renders a page titled **Contributions**, and its helpers live in `composables/utils/contributions.js`. `pages/Disbursement/*` is reached at `/app/payroll` and its components live in `components/pages/Payroll/`. Search for both names when hunting for a feature.

`src/pages/IndexPage.vue` (Quasar scaffold default) is not referenced by any route in `routes.js` — dead code, don't treat it as live. Its former companion `src/pages/PayrollPage.vue` was the pre-Disbursement payroll screen; it and the seven components only it imported (`PayrollStatsCards`, `PayrollRunCard`, `PayrollEmployeePanel`, `PayrollFundingForm`, `PayrollFundingHistory`, `PayrollCreateRunDialog`, `PayrollDetailModal`) were deleted once `pages/Disbursement/*` superseded them — if you find those names in a comment, they refer to code that no longer exists.

**Dead modules elsewhere.** The tree still carries superseded code that looks live, so confirm a file has importers before reading it as the current implementation (`grep -rl ComponentName src`). Currently unreferenced: nine `components/pages/Dashboard/*.vue` files left from earlier dashboard layouts (`AnnouncementsPanel`, `NeedsYourAttentionPanel`, `NotificationsPanel`, `PayrollReadinessPanel`, `PayrollStatusPanel`, `PendingSwapsPanel`, `QuickActionsBar`, `RecentActivityPanel`, `SiteStatusPanel`), `composables/disbursement/stubData.js`, `composables/payroll/usePayoutData.js`, `composables/page/useSwapRequests.js` (the Requests page normalises swaps through `composables/utils/swapRequests.js` instead), `constants/payoutSteps.js` (the live stepper source is `constants/pgiStatus.js`), `composables/admin/index.js` (the barrel has no importers — every consumer imports the individual composables directly), `pages/IndexPage.vue`, and `src/index.template.html` (the *deprecated* Quasar template path — `@quasar/app-webpack` v4 builds from the root `index.html`, and the two have already drifted: only the root one carries the SPA redirect script).

A previous sweep deleted the rest, so if you meet these names in an old comment or plan they refer to code that no longer exists: `common/DataTable.vue` and `common/KpiCard.vue` (generic table/KPI abstractions that were never imported once — pages hand-roll `QTable` with the shared `dash-qtable` classes), `Request/OvertimeRequestTable.vue` (superseded by the near-identically named `RequestOvertimeTable.vue`, which is live), `Attendance/AttendanceFilters.vue`, `Attendance/AttendanceCostCenterEditDialog.vue`, `Schedule/ScheduleStatsCards.vue`, `Dashboard/StatCard.vue` (distinct from the live `DashboardStatCard.vue`), `Payroll/PayrollAcknowledgeDialog.vue`, `Payroll/DisbursementMigrationBadge.vue` and `composables/disbursement/useDisbursementFeatureFlags.js`.

**Boot sequence** (`quasar.config.js` → `boot: ['pinia', 'auth', 'axios', 'toast', 'errorHandler', 'suppressExtensionErrors', 'dialogA11y']`) is order-sensitive: Pinia must init before `auth`, and the auth store must exist before `axios`'s interceptors can read it. `toast` must come before any page can notify (it monkey-patches `Notify.create` / `$q.notify` — see Toasts below) *and* before `errorHandler`, which raises a toast of its own. `errorHandler` sets `app.config.errorHandler`: without it, an exception thrown while Vue renders — typically a dereference of a payload field that turned out null inside a computed — unmounted the subtree, logged a trace and stopped, so a panel or a whole page just went blank with nothing to report. It now names the component and the hook in the console and raises one toast. It deliberately swallows nothing, never retries, and ignores axios cancellations (which are bookkeeping, not faults); `dialogA11y` suppresses the default mousedown focus on Quasar's `QDialog` backdrop, which otherwise parks focus on an `aria-hidden` node and trips a Chrome console warning on every persistent dialog.

**Icons**: `extras` loads `material-icons` *and* `material-icons-outlined`. The `o_` icon prefix resolves to the outlined set, and the nav rail in `MainLayout.vue` relies on it — inactive items use `o_*`, the active one swaps to the filled glyph, so selection is carried by icon weight rather than a highlight. Drop the outlined extra and every `o_*` icon in the app renders blank.

**Auth store naming gotcha**: `useAuthStore` is defined in `src/boot/auth.js` — there is no `src/stores/auth.js`. Always import it as `import { useAuthStore } from 'src/boot/auth'`. Its `state()` runs inside the `auth` boot file, before anything is mounted, so *nothing in it may throw*: a throw there does not degrade a feature, it stops the app from booting on every reload with no UI left to log out from. It rehydrates through `readStoredObject` and persists through a single `persist()` action that removes a key rather than serialising a null-ish value — because `localStorage.setItem(k, JSON.stringify(undefined))` writes the *string* `"undefined"`, which is what used to make the rehydration throw. It holds **both** halves of the SimpleJWT pair — `token` and `refreshToken` (`setRefreshToken`, getter `canRefresh`) — because the refresh token is credential material and the same "never read storage for credentials" rule applies to it. `LoginForm` used to write it to a loose `refresh_token` key that nothing ever read, so a session simply died when the access token expired, and `clearToken()` did not remove it either: logging out left a usable long-lived credential in the browser. The storage key is unchanged, so sessions created before this keep working.

**API layer** (`src/boot/axios.js`): a single shared `api` axios instance. Its request interceptor attaches `Authorization: Bearer <token>` from the Pinia auth store and a Django `X-CSRFToken` header (read from the `csrftoken` cookie) on mutating requests; its response interceptor handles 401 by *refreshing the session* (below), and only ends it when that fails. Always `import { api } from 'boot/axios'` (or `src/boot/axios`) for new network calls.

**A 401 is recoverable, and the session teardown is a real reload.** The interceptor posts the stored refresh token to SimpleJWT's `POST /api/token/refresh/` and replays the original request with the new access token, once per request (`_retriedAfterRefresh`). All 401s in a wave share one refresh promise — parallel requests 401 together, and N concurrent refreshes would spend the token N times and fail each other under `ROTATE_REFRESH_TOKENS` — and a rotated refresh token in the response is stored in place of the one just spent. Only when there is no refresh token, or the refresh itself fails, does `endSession()` clear the store and bounce to login. That teardown **must** reload: the previous line was `window.location.href = '/#/login'`, which from `…/#/app/employees` changes only the fragment, so the browser does a same-document hash navigation and never reloads — the store was cleared but the SPA kept running, and every queued request then went out bare and came back `"Authentication credentials were not provided"`. One expired token produced a screenful of 401s, none of which named the real failure. For the same reason the **request** interceptor refuses to send at all when the store has no token, rejecting locally with `code: 'ERR_NO_SESSION'` (which `extractErrorMessage` renders as a session message) unless the path is in `PUBLIC_PATHS` — login, the refresh call, and the three password-reset endpoints — or the caller passed an explicit `Authorization` header, as the login flow's `useAuth` lookups do. The response interceptor also logs every failure as `[axios error] …`; when an endpoint uses a status as an *answer* rather than a failure — `active-contract` 404s for "no active contract", the attendance audit trail 404s for "nothing recorded yet" — pass `expectedStatuses: [404]` in the request config to keep that log quiet. The promise still rejects, so the caller's own handling is unchanged; use it only where the status is genuinely a normal result, never to hide errors the user should hear about. The request log is dev-only and prints whether the Authorization header is present, never any part of the token itself. `src/composables/utils/http.js` re-exports `api`, the deprecated `BASE` (several composables still import it for URL-building — don't propagate that, but expect to see it), and `extractErrorMessage`. **`authHeaders()` is gone.** It read `localStorage.access_token` directly and returned an Authorization header, so it was a second source of truth for credentials that diverged from the store after `clearToken()` — a request routed through it could still authenticate after logout. All 140 call sites were removed and the function deleted; the interceptor is the only thing that authenticates a request. Same rule for reading the token anywhere else: go through `useAuthStore().token`, never `localStorage` or `sessionStorage` (`boot/auth.js`'s own state initialiser is the single exception).

**Dev proxy** (`quasar.config.js` → `devServer.proxy`): forwards specific path prefixes (`/api`, `/user`, `/organization`, `/communication`, `/attendance`, `/cash_advance`, `/contracts`, `/access`, `/admin`, `/audit`, `/ws/notifications`, and an explicit allowlist of `/payroll/<subpath>` routes) to `API_BASE_URL`. The `/payroll` allowlist is deliberately narrow so it doesn't swallow the SPA's own `/app/payroll` client route. The entries are deliberately grouped rather than one-per-prefix — every plain HTTP prefix shares a single `context` array, `/payroll` keeps its own for legibility, and `/ws/notifications` is separate only because of `ws: true`. http-proxy-middleware attaches a `close` listener to the shared dev server per entry, and one-per-prefix put twelve listeners on one emitter, past Node's default of ten, so `npm run dev` opened with a spurious MaxListenersExceededWarning. When wiring up a new backend endpoint under an existing prefix, no config change is needed; a genuinely new top-level prefix goes into that shared array (not a new object) or `npm run dev` requests to it will 404.

**State management**: Pinia is used sparingly for small persisted/global state (`stores/company.js` for the active company + company list, `boot/auth.js` for the auth store) — both mirror their own state into `localStorage` and rehydrate from it on init. Most feature data-fetching and mutation logic instead lives in `composables/page/*.js`, one composable per feature area (`useEmployees`, `useAttendance`, `useSchedule`, `useRequests`, `usePayroll`, `useDeductions`, `useAnnouncements`, `useInvites`, `useAuth`, `useOrganization`, `useDashboardSummary`, `useRolesAndPositions`, `useAuditLogs`, `useEmployeeBalances` (leave/CTO balance grants, backing the Employees page's leave/CTO balance-assignment modals), etc.), each exposing refs + async functions directly rather than going through a store. Several of these (see `useEmployees.js`) implement their own module-level cache keyed by `companyId` with a TTL and in-flight request de-duplication, plus an `invalidateCache()` called after mutations — follow that shape when adding fetch logic to a composable rather than introducing a new caching mechanism.

**Every bulk write reports per-item outcomes and always refetches.** These endpoints decide one record at a time, so a bulk action is N calls that can partly succeed. Neither `Promise.all` (which rejects on the first failure while the rest keep going) nor a `for await` loop under one `try/catch` is acceptable: both leave earlier records already committed on the server, abort the run, skip the refetch and report a single flat failure — so approved rows keep rendering as pending and a retry re-writes them. Use `Promise.allSettled`, or a per-item `try/catch` inside the loop; count the outcome; refetch unconditionally; and close with three distinct messages for all / some / none. `Disbursement/ReviewPage.vue`'s bulk review and `RequestPage.vue`'s `bulkDecideOvertime` are the reference implementations. `Promise.all` is still right for parallel *reads*, where one failure genuinely invalidates the set.

**Every fetcher that publishes into shared state needs a stale-response guard.** Responses do not arrive in the order they were sent, so a control the user can change faster than the API answers — an attendance date, a schedule week, a contributions cutoff, the workspace switcher — lets an older response land last and overwrite a newer one. Nothing errors; the screen just shows the wrong period, or worse, the wrong company. Take a token from `createRequestToken()` (`composables/utils/requestToken.js`) before the request and check `isCurrent(token)` before committing — `useAttendance`, `useSchedule`, `useDeductions` and `useRequests` all do, one guard per published ref. `usePayroll.js` solves it the other way, with a per-key `AbortController` that cancels the superseded request; prefer that when the in-flight work is expensive enough to be worth cancelling, and the token when the response is cheap or shared through a cache (cancelling a shared request would strand a second caller waiting on it).

Besides `composables/page/`, there are three other composable directories: `composables/admin/` (see below), `composables/disbursement/` (see below), and `composables/payroll/` (currently just `usePayoutData.js`, a thin wrapper around `useDisbursementApi().fetchPayoutGroupInstances`). `composables/useWebSocket.js` and `composables/useNotifications.js` live at the top level of `composables/` (not under `page/`) — see the WebSocket note above.

**`composables/utils/` is two different things.** `http.js` is the API shim described above; the rest splits into generic formatters (`timezone.js`, `calendarDate.js`, `format.js`, `locale.js`, `statusColors.js`) and *per-feature derivation modules* (`manning.js`, `positionRequirements.js`, `contributions.js`, `attendance.js`, `schedule.js`, `employee.js`, `overtimeRequests.js`, `swapRequests.js`, `assignmentHistory.js`). The derivation modules are the load-bearing convention: a feature's payload normalisation and every reading computed from it (gaps, ratios, tone/threshold rules, status labels) live in one module so the page's table, its tablet card list and its summary tiles cannot each invent their own arithmetic and disagree on screen. When adding a figure to a feature that already has such a module, extend the module rather than computing it in the component. `manning.js` is the fullest worked example, and its header comment explains the payload's traps (a null quantity means "no target set", not zero; `needed` / `assigned` / `working` are three distinct readings).

Two of the generic formatters are conventions rather than conveniences, and both are now used everywhere rather than in half the tree:

- **Calendar dates go through `calendarDate.js`.** A `YYYY-MM-DD` in this app is a calendar day, not an instant, and the two obvious ways to produce one both shift it: `new Date().toISOString().slice(0, 10)` gives the *UTC* day (in Manila that is yesterday until 08:00), and `new Date('2026-09-02')` parses as UTC midnight so `toLocaleDateString` renders the day before anywhere west of Greenwich. Use `todayIso()`, `toIso`, `fromIso`, `shiftIso` and `longLabel` from that module — `AttendanceDateRangePicker.vue` and `ScheduleRangeCalendar.vue` each carried a private copy of all of it before. Call `todayIso()` per use rather than caching it in a `ref`, or a tab left open overnight keeps reporting yesterday.
- **localStorage goes through `composables/utils/storage.js`.** `readStoredJson(key, fallback)` / `readStoredObject` / `safeParseJson(raw, fallback)` never throw, and `writeStored(key, value)` removes a key instead of storing `"undefined"` for a null-ish value. The trap the module exists for is narrow and both obvious defences miss it: `JSON.parse(localStorage.getItem(k))` survives a *missing* key (`JSON.parse(null)` is `null`) and so does `|| '{}'`, but neither survives the literal string `"undefined"` — a value this app wrote itself. Four `JSON.parse` sites are deliberately still hand-rolled because their catch branch carries meaning rather than a fallback: `useCompany.js` and `stores/company.js` treat an unparseable value as a legacy bare id, `useWebSocket.js` passes an unparseable frame through as raw text, and `MainLayout.vue` decodes a JWT payload and keeps its cached value on failure. Everything else uses the helpers.
  One *write* still bypasses `writeStored`: `SchedulePage.vue`'s `saveLeaveToStorage` pushes onto the `wagey_leaves` key with a raw `localStorage.setItem` even though the same file reads it back through `readStoredJson`. Worth knowing for two reasons — it is the one place the convention is not yet applied, and `wagey_leaves` is a purely client-side list (leave rows the page keeps for itself), so it is not backed by any endpoint and will not survive a different browser.
- **Error messages go through `extractErrorMessage(error, fallback)`** in `utils/http.js`. It reads DRF's named keys and its `{ field: ["message"] }` shape, refuses an HTML body (Django's 500 page used to land whole inside a toast), and has distinct wording for a 5xx and for a dropped connection. Hand-rolled `error.response?.data?.detail || … || 'Failed'` chains are gone from the codebase; there are two deliberate exceptions, each commented in place — `ReviewPage.vue`'s `serverMessage`, which must be able to return `''`, and `EmployeesPage.vue`'s `addEmployeeErrorMessage`, which prints *every* field error because the add-employee modal marks none of them inline.

`src/constants/` holds shared enum-ish tables for the payroll subtree — the disbursement stepper and status pills read from these rather than hardcoding stage lists. `pgiStatus.js` is the load-bearing one (`computeStepsFromPgiStatus`, `stepRouteForPgiStatus`, `PGI_STATUS_MAP`): it turns a payout-group-instance status into "which step is this run on" for both `PayoutProgressStepper.vue` and the list page's row links. `payoutStatus.js` backs `PayoutStatusBadge.vue`; `payoutSteps.js` has no importers left. `src/services/` exists but is empty; don't put anything there without reason.

**The audit surface is two unrelated endpoints, not one.** `useAuditLogs.js` covers the cross-module admin write log and one attendance record's revisions (below); `useAssignmentHistory.js` backs the Audit Trail page at `/app/audit` and reads `GET /audit/assignment/history/` — one DRF-paginated entry per change to somebody's shift on a day (`updater_name`, `employee_name`, `shift_date`, `new_shift`, `previous_shift`, `updated_at`). They are deliberately separate composables for the same reason the page has its own: the payloads share nothing but the URL prefix. Three things about that endpoint are easy to get wrong. It carries **no company field** and answers company-wide, so unlike the admin log — which re-checks every row — the company query parameter (sent under both `company` and `company_id`) can neither be verified on the way back nor relied on: the trail arrived holding every company the caller could see. The composable therefore narrows the assembled rows against that company's employee roster from `useEmployees` before publishing them — `scopeEntriesToRoster` in `composables/utils/assignmentHistory.js`, matching on `employee_name` because the payload carries no id — and exposes `companyScoped`, which is false only when the roster could not be read, the one case where the page admits other companies may be showing rather than filtering the trail to nothing. Its pages are walked by incrementing `page` on the *relative* path rather than by following the absolute `next` URL, which points at the API host and would step around the dev proxy. And the whole set is assembled before the page filters, sorts and slices it, up to a `MAX_PAGES` cap that the page states out loud when it is hit — sorting a single server page would silently answer a narrower question than the control claims to. `previous_shift` is legitimately null (a *first* assignment, not a missing value) and `updated_at` arrives pre-formatted in the server's timezone, so `composables/utils/assignmentHistory.js` passes it through for display and parses it only to sort.

Two composables are newer than the rest and worth knowing about: `useManning.js` (site manning board — `GET /organization/sites/manning/{company_id}/`, one day at a time) and `useAuditLogs.js` (the audit trail — `GET /audit/admin/logs/` for the cross-module admin write log, plus `GET /audit/attendance/updates/{attendance_uuid}/`, which the Attendance audit dialog uses to answer "who edited this punch, and to what", something the record's own `updated_at` cannot say; that payload carries the punch times as they stood after each save, and the composable diffs each revision against the one before it so the list can show what actually changed). Both demonstrate the expected discipline for company-scoped fetching: resolve `companyId` per request, guard against out-of-order responses with a request token, and verify the response's company/date matches what was asked for before rendering it.

**Multi-tenancy**: nearly every API call is scoped by the active company. Resolve it via `useCompany()` (`composables/page/useCompany.js`, backed by `useCompanyStore`) before building request URLs. Users can belong to multiple companies, switchable via tabs in `MainLayout.vue`'s header. That module exposes two things and the difference matters: `useCompany().companyId` is a **computed** over the store (deliberately not a `ref` snapshot — it used to be one, and consumers created before the workspace switcher settled kept a stale or empty id while other code read the store, so one page could fetch for one company and write to another), while the standalone `resolvedCompanyId()` export is the localStorage fallback, tolerating four historical keys (`selectCompany`, `selectedCompany`, `company_id`, `companyId`) and both raw-string and JSON-object values. Prefer the computed; re-resolve per request rather than capturing the value at setup, and clear company-scoped state (rows, lookup option lists, selected filter ids) when the active company changes.

**One source, always the store.** RequestPage and SchedulePage each used to carry a *private* localStorage resolver alongside the `useCompany()` they already imported, and the copies disagreed with it — SchedulePage's returned `parseInt(raw)`, i.e. `NaN` for a stored object without an `id`, which then went into a request URL as the literal string `NaN`. Both are gone. If you need the id as an integer, derive it from the computed (`parseInt(companyId.value, 10)`), don't re-resolve it.

How a switch propagates, since it is not obvious: `MainLayout.onCompanyChange` calls `companyStore.setCompany()` and then `window.location.reload()`. The reload is *no longer what makes a switch correct* — pages read the store through the computed, so their clear-and-refetch watchers fire on their own — and removing it is safe and would spare a full app boot per switch; it is left in as a decision to take deliberately. A switch made in **another tab** is the one case the store cannot see, because a `storage` event is delivered only to the tabs that did not make the change; `MainLayout` holds a single listener for that which hydrates the store, and every page then reacts through the computed. Don't add a per-page `storage` listener — RequestPage had one, and it meant only that page reacted, and only to the cross-tab case.

**Admin-settings composables** (`composables/admin/*.js`): one composable per admin sub-resource (departments, positions, roles, shifts, sites, cost centers, contracts + contract types, payroll groups, department policies), each following the same list/create/update/delete shape and mostly re-exported together from `composables/admin/index.js` — but this isn't exhaustive, e.g. `useAdminCostCenters.js` is currently missing from that barrel and consumers import it directly. Check the barrel before assuming a composable is exported from it. The newest member is `useAdminSitePositionRequirements.js` (site position requirements — `GET/POST /organization/sites/{site_id}/position-requirements/`, "this site needs N of this position"), reached from `AdminSettingsPanelSites.vue` via `SitePositionRequirementsDialog.vue`, with its normalisation and summary readings in `composables/utils/positionRequirements.js`. It is the *target* side of the Manning board: the endpoint is site-scoped by path with no list-across-sites form, so the Sites table's summary column costs one request per site (batched under a single request token), a requirement is dated (`effective_from`/`effective_to`, the latter legitimately null) so "how many does this site need" must be asked about a particular day, and an absent requirement means *no target set*, not zero — the same trap `composables/utils/manning.js` documents.

**Disbursement (payroll) subsystem**: all six `pages/Disbursement/*.vue` pages now call `composables/disbursement/useDisbursementApi.js` unconditionally. The stub-vs-real migration is finished and its scaffolding has been removed: the per-page feature flags (`useDisbursementFeatureFlags.js`), the sidebar progress badge (`DisbursementMigrationBadge.vue`) and the old `PayrollPage.vue` the flags fell back to are all deleted. `stubData.js` is the last piece still on disk and has no importers. `.opencode/plans/disbursement-redesign-plan.md` describes that flag-gated migration as if it were pending — it is the historical plan for work already shipped, not a spec for the current code.

Two small resolvers exist because the disbursement endpoints answer about figures rather than identity, and both are worth reaching for before inventing a lookup: `composables/disbursement/usePayoutGroupIdentity.js` turns a payout-group-instance id into `{ name, cutoff, status }` for the five step-page headers (no step endpoint returns the run's name), and `composables/page/useEmployeePayoutGroup.js` resolves an employee's payroll group from their *active contract* — used by the Schedule, Attendance, Employees and Requests pages to offer a payout-group filter, since the disbursement API keys everything by cutoff and identifies employees by name rather than id.

**Styling**: only `app.scss` is listed in `quasar.config.js` → `css`, but its last line is `@import './dashboard'`, so `src/css/dashboard.scss` is global too — and despite the name it, not `app.scss`, is the live design system. It defines the `--dash-*` CSS custom properties on `:root` (neutral ramp `--dash-n-25`…`--dash-n-900`, surfaces, `--dash-line*`, `--dash-ink*`, accent, `good`/`warn`/`critical` status sets, and a fixed six-step categorical series ramp) plus the shared primitives: `dash-qtable` (with `--flush` / `--compact` modifiers and per-row `dash-qtable__row*` classes) is how ~30 files get identical table chrome, alongside `dash-panel`, `dash-table`, `dash-scroll-x`, `dash-modal` and the skeleton metrics that `components/common/TableSkeleton.vue` mirrors. Custom properties are the deliberate mechanism: Vue *scoped* style blocks can read them with no import, which is why ~100 components use `var(--dash-*)` and **no component uses the SCSS `$primary` / `$gray-*` variables in `app.scss`** — treat that palette as legacy and reach for the tokens. Pages then add a locally-scoped block with a short page prefix (`ded-`, `dash-`, etc.). `quasar.variables.scss` feeds Quasar's own theme.

**Every dialog is one chrome, and it is global.** `dash-modal` in `dashboard.scss` is the card, head, body and footer that all 44 QDialogs in the app are built from — `.dash-modal` (base 480px, + a width modifier from `--xs` 360 through `--2xl` 820, plus `--confirm` 380) — a wider rung is earned by content that is genuinely two-dimensional, a table or a pair of calendars or a seven-column week, never by a form that merely has a lot of fields, which wants a taller dialog rather than a wider one, `__head` (navy bar: a 38px `__head-icon` tile, `__title`, `__sub`, and the close button), `__body` (white, scrolls, owns the field metrics), and `__foot` (a `--dash-n-25` bar with a quiet `__cancel` and exactly one solid action — `__submit`, `__approve`, or `__danger` on a destructive confirmation). `__stack`, `__grid`, `__field`, `__section` and `__row`/`__label`/`__value` are the content primitives inside a body; a form that needs its buttons pinned wraps body and footer in `__form`. The body scrolls with **no scrollbar** — `scrollbar-width: none` plus a zero-width `::-webkit-scrollbar`. That is the opposite call from `dash-scroll-x`, where the always-drawn track is the affordance that says a table continues sideways; a dialog body is bounded by its own header and pinned footer, so it visibly continues past its edge without one. Scrolling itself is untouched — wheel, trackpad, touch and keyboard all still work.

It is global rather than a component because a QDialog teleports its card to `<body>`, and because three separate copies of this chrome had already grown up in the tree — `Request/requestModal.css`, an `.admin-modal-*` block in `AdminSettings/AdminSettingsPanelShared.scss`, and a per-file version in each Employees / Schedule / Attendance dialog carrying literal hex values. They had drifted into three header heights, four cancel-button treatments and radii of 8 / 12 / 14 / 16px. Those copies are gone; `requestModal.css` survives with only the request-specific content (leave-type chip, swap approval trail).

**The body owns the vertical rhythm, with a flex gap.** `__body` is a flex column with a 14px gap, so a block dropped into a dialog is spaced by where it lands rather than by a margin it carries. Three dialogs used to set `display: flex; gap` privately and the rest relied on whatever margins their parts happened to have, which is how a heading could sit flush against the paragraph above it in one dialog and 20px clear of it in the next. Two consequences worth knowing: `__body > *` is `flex-shrink: 0`, because a scrolling flex column otherwise squashes a tall child (a calendar, a table) instead of letting the body scroll past it; and a body whose content is centred needs `__body--center`, since `text-align` no longer positions a flex item — that is what the two header-less dialogs (invite success, delete confirmation) use. `__body--row` is the one-line variant for a centred loading message.

A titled block inside a body is `__group` (7px gap) with a `__group-label` — sentence case at 12px/600. Use `__group-head` when the label shares its line with an action, like the refresh button on the attendance audit trail or the remove button on a repeated shift row. `__section` is the heavier version that draws a card around itself; a group is just a heading over its content. **No uppercase letter-spaced micro-labels anywhere** — the dialogs were the last place in the app still carrying them (11px/700 at 0.5px tracking), and they are gone.

**Every dialog field is a label above its control, never a floating label.** `__field` is the wrapper, `__field-label` the label (`__req` for the red asterisk on a required one), `__field-hint` an optional line under the control saying what it decides. Adjacent `__field` siblings space themselves, so a body only needs `__stack` or `__grid` when it wants a different rhythm or two columns. All 123 fields across the 26 form dialogs use it.

The reason is mechanical, not stylistic: Quasar's floating label lives *inside* the control, so the control has to be tall enough for two lines of text — that is where its 56px default comes from. Half the dialogs used it and half didn't, which is what made the forms look unarranged: 56px fields sitting next to 34px ones. Moving the label out is what buys the height back, and it is why the in-dialog control is **34px** rather than the 38px the pages use — a dialog is a denser surface, and a six-field form at page density is taller than the dialog holding it. A select's menu matches, via `popup-content-class="dash-popup dash-popup--modal"`. Quasar's `q-mb-md`-style spacing utilities do not belong on a control inside a `__field`: they insert margin between the label and its own input.

Two things about the CSS are load-bearing rather than stylistic. Every width rule is written twice, once compounded with `.q-card` — Quasar caps a dialog card with `.q-dialog__inner--minimized > div`, a two-class selector, so a plain `.dash-modal--lg { width: 600px }` is overruled and every wide dialog silently renders at Quasar's 560px cap. The footer's sibling-margin reset is compounded the same way, against `.q-card__actions--horiz > .q-btn-item + .q-btn-item`. This is why the three systems it replaced each reached for `!important` there.

The confirmations raised with **`$q.dialog({ ... })`** are a separate family — about twenty of them, and not components, so none of those classes can be put on them. `dashboard.scss` restyles the markup Quasar emits under `.q-dialog-plugin` instead: card, title, message, and a footer whose first button is quiet and whose last one is filled (navy, or the system's red when `ok: { color: 'negative' }`). A scoped rule can never reach them — the plugin's card is teleported and carries no `data-v-*` attribute — so two components that tried (`EmployeesPage.vue`, `AdminSettingsPanelShared.scss`) had dead blocks that were removed. A `color:` passed to one of those buttons compiles to a Quasar colour utility that sets its value with `!important` (`.bg-negative` on a filled button, `.text-negative` on a flat one), so the block answers it in kind — the one place in `dashboard.scss` that uses `!important`. Only the tone is honoured, never the weight: the OK button is always the filled one and Cancel always stays quiet, and `warning` is remapped to the brand fill because white on Quasar's #f2c037 fails contrast at any size.

**Don't build a dialog as an HTML string.** `AdminSettingsPanelCustomMultipliers.vue` used to pass thirty lines of markup with eighteen inline hex colours to `$q.dialog({ html: true })`; nothing in the design system could reach it, so it stayed the way the app looked before the system existed. It is `CustomMultipliersConfirmDialog.vue` now. A confirmation carrying real content — here a list of multipliers with before-and-after values — is a component; the plugin is for a question and two answers. There are no `html: true` dialogs left in `src/`.

**Page width is one token with a one-way ladder.** `--dash-page-max` in `dashboard.scss` is the cap `components/layout/PageShell.vue` centres every page within, stepping 1400 → 1600px (≥1440) → 1920px (≥1920) → 2200px (≥2400) so a 2560px screen is not mostly bare canvas; `PageShell`'s `fluid` prop drops the cap for pages whose tables want the whole viewport (`AdminSettingsPage`, `RequestPage`). The ladder's rule is that **every step is a `min-width` query at 1440px or above** — that is what makes widening the app for large monitors safe, since no rule in it is ever evaluated on a phone, a tablet or a 1280px laptop and the small-screen layout therefore cannot regress. Follow that rule for any other large-screen work (grid reflow, relaxed truncation caps): add a `≥1920` query, never edit a declaration that also applies below it, and in particular don't convert the ~16 fixed `repeat(2, minmax(0, 1fr))` panel grids to `auto-fit`, which would change reflow at every width including phones.

Read `dashboard.scss`'s header comment before changing colour: the categorical ramp is a fixed order validated for colour-vision separation (never cycle past `--dash-cat-6`; fold the rest into "Other"), and status colours are reserved — they never stand in for a series hue and never carry meaning without an accompanying label.

**Component organization**: page-specific components live under `components/pages/<PageName>/` mirroring the corresponding `pages/<PageName>Page.vue` (e.g. `components/pages/Employees/EmployeeAddModal.vue` for `pages/EmployeesPage.vue`). Shared, page-agnostic pieces live in `components/common/` (now exactly three files: `StatusPill.vue`, `TableSkeleton.vue` and `AppToast.vue`) and `components/layout/` (`PageShell.vue`, which every page wraps its content in).

A recurring per-feature shape is worth knowing: a feature's list is usually a `<Feature>Table.vue` for desktop plus a `<Feature>CardList.vue` for narrow screens, swapped on `$q.screen.lt.md` in the page (Attendance, Employees, Announcements, Invites, Deductions and Manning all do this). Both renderers must read the same derivation module in `composables/utils/` — that pairing is a large part of why those modules exist. The Requests page adds its own variant: the four tab tables (`RequestLeaveTable`, `RequestOvertimeTable`, `RequestCashAdvanceTable`, `RequestSwapTable`) share toolbar and cell chrome via `<style scoped src="./requestGrid.css">` and share a row action menu via `RequestRowMenu.vue`, so per-tab CSS belongs in the component's own block, not in `requestGrid.css`. The payroll/Disbursement subtree breaks the mirroring rule: pages live at `pages/Disbursement/*.vue`, but their components live under `components/pages/Payroll/` (not `components/pages/Disbursement/`), e.g. `PayoutTable.vue` (the list page), `DisbursementStepShell.vue` / `DisbursementStatRow.vue` / `DisbursementTableCard.vue` (the chrome every step page composes), `EmployeeDetailDialog.vue` and `EmployeeContributionsDialog.vue`.

**The Dashboard is the one page assembled from tabs, and it owns four private layout primitives.** `DashboardPage.vue` renders `DashboardStatsRow.vue` plus four tab components — `TodayTab`, `CurrentCutoffTab`, `MonthlySummaryTab`, `AnnualSummaryTab` — and every other panel is reached through one of those four, which is why `components/pages/Dashboard/` is by far the largest component directory (~40 files) while the page itself imports only six things. Before hand-rolling chrome inside it, note that the directory carries its own primitives that nothing outside it imports: `DashPanel.vue` (the titled card each panel wraps itself in — 16 importers), `DashTable.vue` (the in-panel table — 6), `DashPager.vue` and `DashSkeleton.vue`. They sit here rather than in `components/common/` on purpose, encoding the dashboard's denser panel scale rather than the page-level `dash-panel` / `dash-qtable` chrome — so extend them for a new panel, and don't reach for them from another page. `DonutChart.vue` and `TrendChart.vue` also live here and are the app's only chart components (see below).

**Toasts / notifications**: Quasar's `Notify` UI is *not* used. `src/boot/toast.js` replaces both `Notify.create` and the shared `$q.notify` reference with the queue in `src/composables/useToast.js`, rendered by `src/components/common/AppToast.vue` (teleported to `<body>`, mounted once in `src/App.vue`). Every toast is top-center — the `position` option is deliberately ignored, and so are Quasar's `multiLine`, `html`, `color` and `badge*` options, which the host does not implement. **There are no `$q.notify` call sites left in `src/`** — all ~226 were converted, so `import { useToast } from 'src/composables/useToast'` and `toast.success(...)` / `.error(...)` / `.warning(...)` / `.info(...)` / `.loading(...)` is the only form in the codebase; don't add `$q.notify` back. The shim in `boot/toast.js` stays purely as a backstop, since the Notify plugin is still registered and so `$q.notify` remains callable (`positive/negative/warning/info/ongoing` still map to `success/error/warning/info/loading`). One call uses `toast.notify({ ... })` rather than a named method (`SchedulePage.vue`, where the tone is a ternary). Repeated identical messages collapse onto one card with a counter, hovering the stack pauses every countdown, and at most four cards stay on screen. On top of that, `composables/useLoadedToast.js` (`notifyLoaded(label, count)`) is the convention for "data landed" confirmations — only a page's *primary* data set announces itself, never filter lookups or background enrichment passes, or opening a page would fire a column of near-identical cards.

**Charting and export dependencies**: `echarts` + `vue-echarts` is the charting stack (`components/pages/Dashboard/DonutChart.vue` and `TrendChart.vue`, the only chart components in the app). Use ECharts for a new chart. `chart.js`, `vue-chartjs` and `vuedraggable` used to be declared alongside it with no importers anywhere in `src`; they have been removed from `package.json`, so a reference to them in an older comment or plan doc points at a dependency the project no longer has. `jspdf` + `jspdf-autotable` is the client-side export path, used from `pages/Disbursement/CompletePage.vue` and `DisbursementListPage.vue` — there is no server-rendered PDF.

**Console output survives the production build, deliberately.** `build.uglifyOptions.compress.pure_funcs` in `quasar.config.js` strips `console.log` / `.debug` / `.trace` from a production bundle (there are dozens, including `boot/axios.js`'s per-request logging) but *keeps* `console.warn` and `console.error`. This app ships no error-reporting service, so those calls are the only diagnostic trail a person can copy out of their own console when reporting a problem — don't "tidy" this into a blanket `drop_console: true`, and do reach for `console.warn`/`.error` (not `.log`) when a failure should still be visible in production.

**The dev-server error overlay is filtered.** `devServer.client.overlay.runtimeErrors` drops `ResizeObserver loop completed with undelivered notifications` — a browser notice, not a fault, which Quasar's own `QResizeObserver` (behind `QTable`, `QScrollArea`, `QSelect`, `QTabs`) provokes whenever a layout settles over two observation passes. Unfiltered it blanked the app behind a full-screen overlay in dev. The filter is a single-message predicate on purpose; every other runtime error still stops you.

**Unused Quasar scaffolding**: `quasar.config.js` also configures `ssr`, `pwa`, `cordova`, `capacitor`, `electron`, and `bex` targets (`src-electron/` exists on disk), but the app is actually built and shipped as a plain web SPA — via `dist/spa`, `server.js`, `Dockerfile`, and `docker-compose.prod.yml`. Don't assume the other targets are maintained or wired up unless a task specifically asks about them.
